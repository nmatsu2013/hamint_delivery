# 受発注システム 要件定義書（spec.md）

作成日：2026-11-24 ／ 状態：ドラフト（業務責任者・専門家の確認前）

## 0. この文書について

- 対象：韓国の医療製品（糸リフト、注射針など）を、日本のクリニックから受注し、韓国メーカーへ発注するシステム。
- 元にした資料：
  - 業務システム内製化ワークフロー（要件・業務ルール・受入試験の考え方）
  - master-definitions.md（マスタ・管理テーブル定義書）
  - products-seed.sql（サンプルデータ）
  - 画面デザイン（受注一覧・受注明細）
- 「要確認」は、業務責任者または専門家の判断が必要な項目。推測で確定していない。一覧は第13章。
- 本書の金額・名称は、サンプルデータの値を例に使っている。

## 1. 目的と背景

### 1.1 現状の課題（想定）
- 注文を電話・メール等で受け、Excelで受注・発注・請求を別々に管理している。
- 転記が多く、二重入力や入力ミスが起きる。
- 発注、輸入申請、国際輸送、入庫・検品、国内配送、請求・入金の進み具合が、1か所で見えない。
- ロット番号と使用期限が、どのクリニックに納品されたかをすぐ追えない。
- 製品、顧客、価格が複数のExcelに分散している。

### 1.2 目的
1. 受注から入金までを、受注単位で一元管理する。
2. 誰が何を変更したかを追跡できるようにする。
3. ロット・使用期限・納品先を、回収時にすぐ検索できるようにする。
4. 関税・通関費用などを含めた原価を把握できるようにする（配分方法は要確認）。
5. 脱Excelを進め、データベース化する。

### 1.3 成功の測り方
導入前に、現行業務で次を測定し、試験導入後と比較する。削減効果は未測定。
- 1件あたりの入力時間
- 転記の回数
- 請求の訂正件数
- 進み具合の問い合わせ回数

## 2. スコープ

### 2.1 対象（最初のリリース）
| 区分 | 内容 |
|---|---|
| マスタ | 顧客（クリニック・配送先）、製品、仕入先（メーカー・担当者）、価格 |
| 受注 | 受注登録、受注一覧、受注明細、取消 |
| 発注 | 受注明細に紐づく、韓国メーカーへの発注 |
| 輸入 | 輸入申請、申請書類、通関・関税の記録 |
| 輸送 | 国際輸送（船便・航空便・国際宅配）の追跡 |
| 入庫・検品 | 入庫日、良品・不良・破損数、クレーム対応状況 |
| ロット | ロット番号、使用期限、納品先の記録と検索 |
| 配送 | クリニックへの国内配送、追跡番号、納品日 |
| 請求・入金 | 請求、入金、未入金の確認 |
| 共通 | ログイン、権限、操作履歴、CSV出力 |

### 2.2 対象外（後続）
- 在庫管理（棚卸、安全在庫、発注点、在庫の引当・差異管理）。本システムは受注に紐づく発注型で、在庫を持たない前提。
- 会計ソフトとの連携、請求書の自動送信、メールの自動送信。
- EDI、需要予測。
- 特注品の専用管理（OEM・特注スレッドは、通常の製品として登録して扱う）。
- 医師単位の管理（医師マスタは作らない）。
- 患者情報の取り扱い（本システムでは扱わない前提。要確認）。

### 2.3 前提
- 利用者は最初は少人数（数名）。
- 正式切替までは、旧Excelを正とする。
- 日本での輸入・販売に必要な許可・届出、薬機法上の区分は専門家が確認する。本システムはその判断をしない（記録のみ）。

## 3. 業務フロー

### 3.1 全体の流れ（to-be）

```
受注 → 発注 → 輸入申請 → 国際輸送・通関 → 入庫・検品 → ロット登録
   → 国内出荷・配送 → 納品 → 請求 → 入金
```

### 3.2 各工程の内容

| No. | 工程 | 担当 | 主な操作 | 主なデータ |
|---|---|---|---|---|
| 1 | 受注 | 営業 | 顧客・配送先・製品・数量を入力。単価は自動で入る | sales_orders / sales_order_lines |
| 2 | 発注 | 購買 | 受注明細から発注を作成。数量・仕入先を確認して確定 | purchase_orders / purchase_order_lines |
| 3 | 輸入申請 | 購買 | 書類を揃えて申請、確認状況を更新 | import_applications / import_documents |
| 4 | 国際輸送・通関 | 購買 | 輸送手段、AWB/BL、ETD/ETA、通関・税額を記録 | shipments（国際輸送）/ import_applications |
| 5 | 入庫・検品 | 倉庫 | 入庫日、良品・不良・破損数、クレームを記録 | purchase_order_lines |
| 6 | ロット登録 | 倉庫 | ロット番号・使用期限を登録 | lots / lot_movements |
| 7 | 国内出荷 | 倉庫 | ロットを選んで出荷登録、追跡番号を入力 | shipments（国内配送）/ shipment_lines |
| 8 | 納品 | 倉庫 | 納品日を記録 | shipments |
| 9 | 請求 | 経理 | 請求を作成（正式発行は経理の確認後） | invoices / invoice_lines |
| 10 | 入金 | 経理 | 入金を登録、未入金を確認 | payments |

### 3.3 例外の扱い
| 例外 | 扱い（案。要確認は第13章） |
|---|---|
| 受注の取消 | 未出荷分のみ可。発注済みの場合は、メーカーへの取消可否と費用を確認 |
| 数量の変更 | 発注前は自由に変更。発注後は、変更履歴を残し、購買が確認 |
| 分納 | 出荷を複数回に分けて登録できる |
| 部分入荷 | 同じ発注明細が複数回に分かれて入荷する場合の扱いは要確認 |
| 検品で不良・破損 | 良品数のみをロットに登録。クレーム対応状況を記録 |
| 単価の変更 | マスタを変えても、過去の受注の確定単価は変わらない |
| 請求後の訂正 | 削除せず、訂正した履歴を残す |
| 輸入申請の差戻し | 状態を「差戻し」にし、理由を備考に残す |

| 購買 | 発注、輸入申請、国際輸送、通関情報の登録 |
| 倉庫 | 入庫・検品、ロット登録、国内出荷、納品の記録 |
| 経理 | 請求、入金、金額・帳票の確認 |
| 管理者 | マスタの管理、ユーザーと権限の管理、操作履歴の閲覧 |

### 4.2 権限の原則
1. 画面の表示だけでなく、サーバーとデータベース（RLS）で制御する。
2. 未ログインでは、業務データを一切取得できない。
3. 権限外の操作は拒否され、データも変化しない。
4. 仕入価格・原価は、営業に表示しない（要確認）。
5. 操作履歴は、通常ユーザーが改変・削除できない。

## 5. 機能要件

### 5.1 共通
- F-01 ログイン・ログアウト。多要素認証を有効にする。
- F-02 全画面で、役割に応じてメニューを出し分ける。
- F-03 すべての登録・更新・取消を、操作者・日時・変更前後つきで記録する。
- F-04 一覧は、検索・状態での絞り込み・並べ替え・CSV出力ができる。
- F-05 数量は1以上の整数、金額は0以上。範囲外は拒否する。
- F-06 確定済みの取引は削除できない。訂正は履歴を残して行う。

### 5.2 受注一覧画面（デザイン済み）
目的：受注の進み具合を、一覧で確認する。

**件数カード**
| カード | 集計の定義 |
|---|---|
| 本日の受注 | 受注日が当日の件数 |
| 発注待ち（受付） | 状態が「受付」の件数 |
| 輸入・輸送中 | 状態が「輸入・輸送中」の件数 |
| 未入金 | 請求済みで、入金が完了していない請求の件数 |

**一覧の項目**：受注日、状態、受注番号、顧客（配送先）、主な製品（先頭1点＋「ほか○点」）、数量（合計）、金額（税抜）、希望納期、入金（未請求／未入金（請求済）／入金済）。

**操作**
- 状態での絞り込み（すべて／受付／発注済／輸入・輸送中／出荷済／完了）。
- 顧客名・受注番号・製品名で検索。
- 「明細を開く」で受注明細画面へ。
- 「新規受注」で受注登録画面へ。

### 5.3 受注明細画面（デザイン済み）
目的：1件の受注について、受注から入金までを確認・操作する。

**進み具合（8段階）**
| 段階 | 完了の判定 |
|---|---|
| 受注 | 受注の登録 |
| 発注 | 発注の確定（発注日） |
| 輸入申請 | 輸入申請の確認状況が「承認」 |
| 輸送・通関 | 国際輸送の納品日、または通関の許可 |
| 入庫・検品 | 入庫日と良品数の登録 |
| 出荷 | 国内配送の発送日 |
| 納品 | 国内配送の納品日 |
| 入金 | 請求金額に対する入金が完了 |

**表示内容**
- 受注情報：顧客、配送先、受注日、希望納期、支払条件、備考。
- 受注明細：製品、規格、数量、確定単価、金額、明細ごとの状態と発注番号。
- 合計：小計（税抜）、消費税、合計（税込）。税区分・端数処理は要確認。
- 関連情報：発注、輸入申請・輸送、入庫・検品・出荷、請求・入金。

**操作**：受注を編集、明細を追加、出荷を登録（権限のある役割のみ）。

### 5.4 受注登録（新規受注）
- F-10 顧客を選ぶと、配送先の候補が出る。既定の配送先が初期選択される。
- F-11 製品を選ぶと、単価が自動で入る（顧客別単価 → 標準単価の順）。単価は受注明細に確定単価として保存する。
- F-12 有効でない製品は選べない。
- F-13 受注番号は自動採番（例：so + 年月日 + 連番）。
- F-14 保存時、受注の状態は「受付」、明細の状態も「受付」になる。

### 5.5 発注
- F-20 状態が「受付」の受注明細から、発注候補を作る。
- F-21 発注は仕入先ごとにまとめる。発注明細は、受注明細に1対1で紐づく。
- F-22 購買が、数量と仕入先を確認して「発注済」に確定する。確定時に、発注日・通貨・金額を保存する。
- F-23 仕入単価は、発注時の仕入価格を発注明細に保存する。
- F-24 発注の確定で、対応する受注明細と受注の状態が「発注済」になる。
- F-25 メーカーへの発注書の自動送信は、初期版では行わない。PDF出力のみ。

### 5.6 輸入申請・通関
- F-30 発注ごとに輸入申請を作成する。申請番号は自動採番。
- F-31 申請書類（インボイス、パッキングリストなど）を登録する。ファイルは、アクセス権を制限した保存領域に置く。
- F-32 確認状況：書類準備中／申請済／確認中／承認／差戻し。
- F-33 通関情報：通関業者、輸入許可日、申告番号、課税標準額、関税、輸入消費税、通関手数料、その他費用（送料・保険など）を記録する。
- F-34 品目別の関税額は、発注明細に記録する。申請の関税合計と一致することを確認する。
- F-35 申請の種類と必要書類は専門家の確認後に確定する（要確認）。

### 5.7 国際輸送
- F-40 発注ごとに国際輸送を登録する。輸送手段、配送業者、AWB/BL番号、ETD、ETA、発送日、納品日（入荷日）。
- F-41 発送日が入ると、受注の状態が「輸入・輸送中」になる。
- F-42 ETAを過ぎても納品日が空の発注を、一覧で確認できる（遅延の確認）。

### 5.8 入庫・検品・ロット
- F-50 倉庫が、発注明細ごとに入庫日、良品数、不良数、破損数、クレーム対応状況を記録する。
- F-51 良品数について、ロット番号と使用期限を登録する。使用期限が空のロットは登録できない。
- F-52 ロットは、製品＋ロット番号で一意。
- F-53 ロットの入庫・出荷・返品・廃棄・調整は、すべて動きとして記録する（改変不可）。
- F-54 入庫・検品が完了すると、受注明細の状態が「入荷済」になる。
- F-55 ロット番号で検索すると、納品先（顧客・配送先）、数量、出荷日の一覧が出る。回収時に使う。

### 5.9 国内出荷・配送
- F-60 出荷は、入庫済みのロットを選んで登録する。受注明細の数量を超える出荷はできない。
- F-61 出荷は、使用期限の近いロットから出す（先入先出）。違うロットを選ぶ場合は、理由を記録する（要確認）。
- F-62 配送業者、発送日、追跡番号、納品日を記録する。
- F-63 発送日が入ると受注の状態が「出荷済」になる。
- F-64 分納を許容する。すべての明細が出荷されるまでは「出荷済」にならない。
- F-65 同じ出荷確定を二重に送信しても、1回だけ処理される。
- F-66 輸入申請が「承認」でないと、出荷できない運用とするか要確認。

### 5.10 請求・入金
- F-70 出荷済みの受注明細から請求を作成する。請求は顧客単位で、締日・支払条件に従う。
- F-71 請求金額は税込、請求明細の金額は税抜で保持する。税区分・端数処理は要確認。
- F-72 入金を登録すると、請求の状態が「一部入金」または「入金済」になる。
- F-73 未入金額は保存せず、請求金額と入金合計から算出する。
- F-74 入金済みになると、受注の状態が「完了」になる。
- F-75 請求書の正式発行は、経理の確認後。自動送信はしない。

### 5.11 マスタ管理
- F-80 顧客：クリニックと配送先（1対多）。
- F-81 製品：型番、素材、太さ、長さ、規格メモ、用途、主力区分、HSコード、ロット・使用期限管理。
- F-82 仕入先：メーカーと担当者（1対多）。
- F-83 価格：仕入価格（韓国ウォン）、輸入代行価格、標準単価、顧客別単価。有効期間つきで履歴を残す。期間の重複は不可。
- F-84 削除はせず、有効フラグで無効化する。
- F-85 マスタの変更は管理者のみ。

### 5.12 状態の定義

**受注の状態**：受付 → 発注済 → 輸入・輸送中 → 入荷済 → 出荷済 → 完了。いずれの段階でも、条件を満たせば「取消」。

| 遷移 | 条件 |
|---|---|
| 受付 → 発注済 | 発注の確定 |
| 発注済 → 輸入・輸送中 | 国際輸送の発送日の登録 |
| 輸入・輸送中 → 入荷済 | 入庫・検品の完了 |
| 入荷済 → 出荷済 | 国内配送の発送日の登録 |
| 出荷済 → 完了 | 入金の完了 |

受注の状態は、明細の状態から決める（複数明細で進み具合が違う場合は、最も遅い明細に合わせる。要確認）。

**請求の状態**：未請求／請求済／一部入金／入金済。
**発注の状態**：下書き／発注済／一部入荷／入荷完了／取消。
**輸入申請の状態**：書類準備中／申請済／確認中／承認／差戻し。
**国内配送・国際輸送の状態**：準備中／発送済／納品済／不達。
**ロットの状態**：使用可／保留／回収。

## 6. 業務ルール

1. 単価は、顧客別単価があればそれを、なければ標準単価を使う。受注時に明細へ保存し、後日のマスタ変更で過去金額が変わらない。
2. 受注明細と発注明細は1対1で紐づける。紐づかない発注はしない（余剰の入荷は要確認）。
3. 確定済みの取引（受注・発注・請求・入金）は削除しない。訂正は履歴を残す。
4. 金額は小数の誤差が出ない型で扱う。韓国ウォンと円は、通貨を必ず併記する。
5. ロットと使用期限は、すべての製品で管理する（機器を除く）。
6. 使用期限切れのロットは出荷できない。
7. 検品で不良・破損と判断した数量は、ロットに登録しない。
8. 請求書の発行、メーカーへの発注書の送付は、人が内容を確認してから行う。
9. 原価＝仕入価格（円換算）＋輸入代行費用＋関税＋輸入消費税＋通関手数料＋送料など。品目への配分方法は要確認。
10. 為替レートの扱い（発注時／月次固定／入荷時）は要確認。

## 9. 非機能要件

### 9.1 セキュリティ
- NFR-01 全テーブルでRLSを有効化し、役割ごとに許可する。
- NFR-02 未認証のアクセスで、業務データを取得できない。
- NFR-03 秘密キー（Supabaseのサービスキーなど）は、サーバー処理だけで使い、ブラウザ・Git・AIへの指示に入れない。
- NFR-04 操作履歴（誰が・いつ・何を・変更前後）を保存し、通常ユーザーは改変できない。
- NFR-05 申請書類などのファイルは、アクセス権を制限した保存領域に置く。
- NFR-06 顧客情報、仕入価格の分類と、アクセス・保存期間・削除の方針を決める（要確認）。

### 9.2 運用・可用性
- NFR-10 バックアップを取り、隔離環境への復元試験を行う。
- NFR-11 エラーログ・DB監視・通知先・障害時の連絡先を設定する。ログに個人情報やキーを出さない。
- NFR-12 本番・検証・開発の環境を分離する。
- NFR-13 利用者は数名。画面の表示は2秒以内を目安にする（要確認）。

### 9.3 データ保持
- ロット・納品先の記録、取引記録の保存期間は、専門家に確認して決める（要確認）。

### 9.4 使いやすさ
- NFR-20 主要画面は、PCのブラウザで使えること。スマートフォンでの閲覧は、受注一覧・明細のみ対応を目標とする。
- NFR-21 文字の大きさ・コントラストは、読みやすさを優先する。
- NFR-22 日本語表示。製品名は、韓国語・英語名も保持する。

一つでも重大項目が未達ならNo-Go。

## 12. 開発の段階（MVPと後続）

| 段階 | 内容 |
|---|---|
| MVP | ログイン・権限、マスタ、受注（一覧・明細・登録）、発注、操作履歴 |
| 追加1 | 輸入申請、国際輸送、通関・関税 |
| 追加2 | 入庫・検品、ロット、国内出荷・配送 |
| 追加3 | 請求・入金、帳票PDF、CSV出力 |
| 後続 | 会計連携、メール送信、原価の自動配分、入荷用テーブルの分離（必要なら） |

進め方：認証 → マスタ → 受注 → 発注 → 輸入・輸送 → 入庫・ロット → 出荷 → 請求・入金。機能ごとに、画面を触る → 架空データで検証 → 差分確認 → テスト → PRを繰り返す。外部の専門家レビューは、DB設計時と本番判定時の最低2回。

## 14. 用語

| 用語 | 意味 |
|---|---|
| 受注 | クリニックからの注文 |
| 発注 | 韓国メーカーへの注文 |
| 国際輸送 | 韓国から日本への輸送（入荷） |
| 国内配送 | 日本国内で、クリニックへ届ける配送 |
| 通関 | 輸入の申告と許可の手続き |
| HSコード | 通関で使う品目の分類コード |
| AWB／BL | 航空貨物運送状／船荷証券（輸送の追跡番号） |
| ETD／ETA | 出発予定日／到着予定日 |
| ロット | 製造のまとまり。番号と使用期限を持つ |
| トレーサビリティ | 製品が、どのロットでどこへ納品されたかを追えること |
| RLS | データベース側で、行ごとにアクセスを制限する仕組み |
| MVP | 最初に作る、最小限の機能の範囲 |
